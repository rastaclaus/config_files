# config_files

> Русский перевод `README.md`. **Источник истины — `README.md`**: при расхождении
> верен английский текст. Этот файл может отставать после правок английской
> версии. Команды, имена файлов, ключи конфигов и hex-значения не переводятся и
> совпадают с `README.md` дословно.

Личные dotfiles. Одна ветка, всё host-специфичное — в `hosts/`.

## Структура

```
fish/ helix/ nvim/ opencode/ direnv/ ghostty/ alacritty/ rofi/ darkman/
networkmanager-dmenu/ xdg-desktop-portal/ applications/
sway/ niri/ ironbar/ waybar/ wayland/                 # Wayland-сессии (gui)
theme/dark/ theme/light/                              # цветовые палитры
darkman/theme                                         # единственный хук darkman
.tmux.conf .ruff.toml                                 # общее (base)
vpn/                                                  # скелет VPN-профиля (см. ниже)
hosts/
  desktop/  ambb/  alen/  work/                       # host-специфичные оверрайды
install/
  install.sh         # установщик
  lib.sh             # общие хелперы (определение хоста, манифесты)
  cleanup.sh         # удаляет пакеты, которых нет в манифестах
  install_vpn.sh     # установщик VPN-профиля (ntech)
  hosts.conf         # hostname -> каталог хоста + профиль
  symlinks.conf      # карта src -> target (+ теги gui/merge)
  volatile.conf      # runtime-файлы, копируемые в merge-каталоги, а не линкуемые
  protected.txt      # системные пакеты, которые cleanup.sh никогда не удаляет
  cleanup-paths.conf # остаточные config/state-пути по пакетам
  verify.sh          # проверки только на чтение
  packages/*.txt     # списки pacman / AUR (см. ниже)
  npm.txt            # глобальные npm-пакеты
  uv-tools.txt       # список для uv tool install
```

Манифесты пакетов (официальный репозиторий + его AUR-аналог):

| файл                       | ставится на                        |
|----------------------------|------------------------------------|
| `packages/base.txt`        | каждый хост (включая headless)     |
| `packages/dev.txt`         | профиль `gui` (на headless — опционально) |
| `packages/gui.txt`         | только профиль `gui`               |
| `packages/aur/base.txt`    | AUR-версия `base.txt`              |
| `packages/aur/dev.txt`     | AUR-версия `dev.txt`               |
| `packages/aur/gui.txt`     | AUR-версия `gui.txt`               |
| `hosts/<host>/packages.txt`| дополнительные официальные пакеты хоста |
| `hosts/<host>/packages-aur.txt`| дополнительные AUR-пакеты хоста |

Host-специфичные исключения для cleanup лежат в `hosts/<host>/keep.txt` (см.
**Cleanup** ниже).

`base` содержит всё, что должно быть на **каждом** хосте, включая headless —
поэтому `docker`, `docker-buildx`, `docker-compose` и `kubectl` живут там: их
дерево зависимостей (79 пакетов, ~600 МиБ) не содержит GUI-библиотек. Всё, что
тянет Chromium, GTK, Mesa или OpenCV, остаётся в `gui.txt`: `chromium`
(используется wrapper-записями в `applications/`), `mermaid-cli` (зависит от
`chromium`) и `ueberzugpp` (зависит от `opencv`/`ffmpeg`). Когда они лежали в
`base`, headless-установка притаскивала 163 лишних пакета (~1.5 ГиБ).

Общие конфиги лежат в корне репозитория; хост приносит только то, что
переопределяет.

Соответствие путей для host-оверрайдов (используется установщиком):

| target                | файл хоста                         |
|-----------------------|------------------------------------|
| `~/.config/<x>`       | `hosts/<host>/config/<x>`          |
| `~/.local/share/<x>`  | `hosts/<host>/local-share/<x>`     |
| `~/<x>`               | `hosts/<host>/home/<x>`            |

Если оверрайд хоста существует, `~/.config/<x>` становится настоящим каталогом,
записи которого — симлинки в репозиторий (сначала общие, при конфликте побеждает
хост). Три записи несут тег `merge` и всегда раскладываются именно так
(`~/.config/fish`, `~/.config/helix`, `~/.config/opencode`): приложения должны
иметь возможность писать рядом с отслеживаемыми файлами (fisher ставит плагины,
fish перезаписывает `fish_variables`, helix может добавлять runtime-файлы,
OpenCode запускает `bun install` для зависимостей плагинов в своём каталоге
конфига). Всё остальное — один симлинк. Файлы из `install/volatile.conf`
копируются в merge-каталог вместо линковки, чтобы записи никогда не попадали в
репозиторий.

## Композиторы (sway / niri)

Оба композитора ставятся для профиля `gui`. На TTY (tty1) fish запускает
композитор, указанный в `~/.local/state/dotfiles/compositor` (`sway`, `niri` или
`none`). Значение записывает установщик из колонки `compositor` в
`install/hosts.conf`, а дальше им владеет `wm` — поэтому правка этой колонки не
переключает уже настроенный хост. `none` означает «без композитора» и
принудительно ставится для профиля `headless`. niri запускается через
`niri-session`:

```sh
wm niri    # переключить к следующему логину
wm sway
wm none    # только консоль: не запускать композитор на tty1
```

Если выбранный композитор не установлен (или в state-файле мусор), fish печатает
сообщение и оставляет рабочую оболочку вместо завершения сессии. Этот файл —
единственный источник истины: старая универсальная переменная `WAYLAND_COMPOSITOR`
удалена, и установщик стирает её (вместе с копией в окружении
`systemd --user`), если находит.

Слои повторяют остальной репозиторий:

- `sway/config`            — общий конфиг sway (`include` хостового `config.d/`).
- `niri/config.kdl`        — общий конфиг niri, с `include "config.d/..."`.
- `hosts/<host>/config/{sway,niri}/config.d/` — выводы/вводы конкретного хоста.

Общие Wayland-хелперы (не зависят от композитора, определяют его в рантайме)
лежат в `wayland/` (`theme-switch` живёт в `applications/`, так как работает и
на headless-хостах):

- `compositor-env.sh` — sourceable-хелпер, который находит **живой** сокет
  композитора. `darkman.service` переживает композитор, поэтому переданные ему
  `NIRI_SOCKET` / `SWAYSOCK` могут указывать на сокет от предыдущего запуска
  niri/sway; хелпер откатывается к самому свежему
  `$XDG_RUNTIME_DIR/niri.wayland-*.sock` / `sway-ipc.*.sock` и проверяет его
  реальным IPC-запросом, экспортируя рабочее значение для дочерних процессов.
  `theme-sync` переопределяет сокет при каждом переключении — именно поэтому
  обои и Mattermost следуют за `darkman toggle` даже после перезапуска niri.
- `wallpapers.sh` — обои через `awww` (с откатом на `swaybg`) на каждом активном
  выходе; выбирает только файлы `*_dark.*` или `*_light.*` под текущую тему
  (см. `Runtime state`), и кэширует половины панорамной картинки в
  `~/Wallpapers/.slices/<layout>/`, чтобы их не резать заново. Каждая смена также
  показывает уведомление с именем исходного файла (`WALLPAPER_NO_NOTIFY=1`
  отключает).
- `toggletouch.sh` — переключение тачпада (`niri msg action toggle-touchpad` или
  `swaymsg input ... events`).
- `mattermost-theme <mode>` — тема чата и окна для Mattermost Desktop,
  вызывается из `theme-sync` (см. **Runtime state** ниже).
- `./applications/theme-switch [dark|light]` — ручное переключение темы; обёртка
  над `theme-sync` (работает и на headless, см. **Runtime state**).

Статус-бар — **ironbar** на обоих композиторах. Один `ironbar/config.yaml`
работает и в sway, и в niri — модули `workspaces` и `focused` определяют
композитор в рантайме, поэтому разделения по композиторам нет. `ironbar/style.css`
в репозитории содержит только раскладку; палитра приходит через сгенерированную
обёртку в `~/.local/state/dotfiles/ironbar/style.css`, поэтому оба композитора
запускают его как `ironbar -t <state>/ironbar/style.css` (см. `Runtime state`
ниже). Ironbar следит за обёрткой и перезагружается при смене темы. Модуль
`battery` скрыт через `show_if` на хостах без батареи и зависит от **upower** (в
отличие от waybar, который читал sysfs напрямую). Погода берётся из общего скрипта
`waybar/weather.py`, вызываемого с `--plain` (по умолчанию вывод — JSON для
waybar).

Прежняя конфигурация **waybar** сохранена в `waybar/`, а строки запуска в
`sway/config` / `niri/config.kdl` закомментированы, поэтому возврат — правка в
одну строку. `install/packages/gui.txt` и `install/symlinks.conf` по-прежнему
несут оба бара.

Порталы: sway оставляет `xdg-desktop-portal-wlr`, niri использует
`niri-portals.conf` (бэкенд скринкаста GNOME).

Переключение dark/light ведёт **darkman**: единственный хук
`~/.local/share/darkman/theme` (симлинк на `darkman/theme`) показывает уведомление
и запускает `wayland/theme-sync`, который переписывает runtime state и затем
запускает по одному скрипту на приложение из `wayland/theme-hooks.d/` (см.
`Runtime state` ниже). Qt-приложения следуют за GTK-темой через GTK platform
theme QT, которая читается из окружения — это ручной шаг на один раз, так как
репозиторий не управляет `/etc/environment`:

```sh
sudo sed -i '/^QT_QPA_PLATFORMTHEME=/d' /etc/environment
echo 'QT_QPA_PLATFORMTHEME=gtk3' | sudo tee -a /etc/environment
```

Qt style engine (Kvantum) не используется: это был единственный пакет, тянувший
Qt-стек в GUI-список, и его хук darkman всё равно не мог работать — хуки
запускаются дочерними процессами, поэтому `export` внутри них никогда не
достигает сессии.

Привязки клавиш синхронизированы между `sway/config` и `niri/config.kdl`
(`Mod`+h/j/k/l, рабочие пространства `Mod`+1..0, терминал/лаунчер, скриншоты,
медиа-клавиши). `Mod`+`Return` запускает **ghostty**, `Mod`+`Shift`+`Return` —
alacritty, который остаётся установленным как fallback-терминал. Возможности
только для sway, которым у niri нет эквивалента (сплиты, stacking, focus-parent,
scratchpad, режим ресайза), остаются в `sway/config`.

## Ghostty

Основной терминал (`Mod`+`Return`); alacritty остаётся на `Mod`+`Shift`+`Return`
как fallback. `~/.config/ghostty` — симлинк на `ghostty/`, конфиг —
`config.ghostty`, палитры — `ghostty/themes/gruvbox-{dark,light}`. Тема,
шрифт, прозрачность и проверки соответствия ghostty↔alacritty описаны в
**Runtime state** ниже — этот раздел про использование терминала.

Проверенная версия: **1.3.1**. Опции и actions зависят от версии: сверяйтесь с
`ghostty +list-actions` / `ghostty +show-config --docs`, прежде чем доверять
сниппету из интернета.

### Чего нет в alacritty

| возможность            | примечания                                                           |
|------------------------|----------------------------------------------------------------------|
| key tables             | модальный ввод — именно это заменяет vi-режим alacritty (ниже)       |
| shell integration      | метки OSC 133/1337: прыжки по промптам, корректный `cwd` для новых табов/сплитов |
| kitty keyboard protocol| приложения (helix, neovim) могут запрашивать физические клавиши, release-события и т.п. |
| command palette        | `ctrl+shift+p`, нечёткий поиск по всем action                        |
| inspector              | `ctrl+shift+i` — TUI-дамп состояния терминала, включая содержимое экрана |
| встроенный поиск       | `ctrl+shift+f` по экрану терминала и его скроллбеку                  |
| `reload_config`        | `ctrl+shift+,` — большинство опций применяется без перезапуска       |
| табы и сплиты          | рисуются внутри одного окна; композитор по-прежнему видит один тайл  |

Сознательно отсутствует: vi-курсора по скроллбеку нет (см. **Scrollback**),
русских раскладок пока нет (таблица alacritty не портирована; приложения с
kitty-протоколом вроде helix работают, потому что получают физические клавиши, а
fish/readline — нет).

### Клавиши, которые стоит знать

Все привязки перечисляет `ghostty +list-keybinds` (`--default` — стоковый набор,
`--docs` — с описаниями).

| клавиши                       | действие                                          |
|-------------------------------|---------------------------------------------------|
| `ctrl+shift+c` / `ctrl+shift+v` | копировать выделение (как `mixed`) / вставить CLIPBOARD |
| `ctrl+insert` / `shift+insert`  | копировать выделение (как `mixed`) / вставить PRIMARY |
| `ctrl+shift+a`                | выделить всё                                      |
| `ctrl+shift+y`                | **наше**: выделить всё + скопировать как `plain`   |
| `ctrl+alt+o`                  | **наше**: весь скроллбек → файл → nvim в новом окне (см. **Дамп скроллбека**) |
| `ctrl+alt+shift+j`            | видимый экран → файл → nvim в новом окне (стоковая привязка) |
| `ctrl+shift+space`            | **наше**: войти в `scroll-mode` (см. ниже)         |
| `shift+page_up` / `shift+page_down` | прокрутить на страницу                      |
| `shift+home` / `shift+end`    | в начало / в конец                                |
| `ctrl+shift+page_up/down`     | к предыдущему / следующему промпту (нужен shell integration) |
| `ctrl+shift+f`, затем `escape` | поиск, завершить поиск                           |
| `ctrl+=` / `ctrl+-` / `ctrl+0`| размер шрифта +1 / −1 / сброс                     |
| `ctrl+shift+t` `ctrl+shift+n` | новый таб / новое окно                            |
| `ctrl+shift+o` `ctrl+shift+e` | сплит вправо / сплит вниз                         |
| `ctrl+alt+arrows`             | перейти между сплитами                            |
| `ctrl+shift+w` `ctrl+shift+q` | закрыть таб / выйти из ghostty                    |
| `ctrl+,` / `ctrl+shift+,`     | открыть конфиг / перечитать конфиг                |

`ctrl+shift+space` для `scroll-mode` выбран не случайно: это триггер
`ToggleViMode` по умолчанию в alacritty, поэтому мышечная память переносится
между двумя терминалами.

Минимальная шпаргалка:

```text
выделить мышью            → shift+insert (PRIMARY) | ctrl+shift+c → ctrl+shift+v (CLIPBOARD)
весь скроллбек в буфер    → ctrl+shift+space, y
весь скроллбек в nvim     → ctrl+alt+o  (новое окно ghostty; внутри TUI — нет, см. ниже)
весь скроллбек в файл     → ctrl+shift+space, w  (в буфере путь → nvim ctrl+shift+v)
видимый экран в nvim      → ctrl+alt+shift+j
листать без мыши          → ctrl+shift+space, затем j/k, ctrl+d/ctrl+u, g/shift+g
поиск                     → ctrl+shift+f  (внутри scroll-mode: /, n, shift+n)
прокрутка внутри tmux     → prefix [  (vi-клавиши), y/Enter — копировать
вся история панели в nvim → prefix e
```

### Скроллбек

`scrollback-limit` измеряется в **байтах**, а не в строках (активный экран тоже
считается, память выделяется лениво, лимит — на один surface): `20_000_000`
замерено на 1.3.1 в окне шириной 1280 px (~150 колонок) — примерно 10 700 строк,
что близко к `scrolling.history = 10000` в alacritty. В более узком окне влезет
больше строк, в более широком — меньше. Скроллбек живёт только в памяти: он не
переживает перезапуск ghostty и никуда не пишется.

Читать его без мыши — `ctrl+shift+space` входит в key table `scroll-mode` (key
tables появились в 1.3; vi-курсора нет, поэтому это прокрутка, а не
редактирование):

| клавиша            | действие                                                |
|--------------------|---------------------------------------------------------|
| `j` / `k`          | на строку вниз / вверх                                  |
| `ctrl+d` / `ctrl+u`| на полстраницы                                          |
| `space`, `ctrl+f` / `ctrl+b` | на страницу                                    |
| `g` / `shift+g`    | в начало / в конец                                      |
| `]` / `[`          | к следующей / предыдущей метке промпта (`jump_to_prompt`) |
| `/`, `n` / `shift+n` | открыть поиск, следующий / предыдущий хит             |
| `y`                | весь скроллбек → буфер как plain-текст                  |
| `w`                | весь скроллбек → файл, **путь** → буфер                 |
| `q`, `escape`      | выйти из режима                                         |

Четыре вещи, в которых легко ошибиться при правке этой таблицы:

* `activate_key_table`, **не** `activate_key_table_once` — одноразовая таблица
  деактивируется первой же сработавшей привязкой, так что `j` прокрутил бы ровно
  один раз.
* `catch_all=ignore` обязателен: поиск привязки идёт из самой внутренней таблицы
  наружу, и без него каждая незабинженная клавиша утекает в шелл (и в работающий
  TUI), вместо того чтобы быть проглоченной режимом.
* Заглавные буквы конфликтуют из-за складывания регистра в ghostty: `g` и `G` —
  один и тот же триггер, поэтому нужно `shift+g` (так же для `shift+n`).
* Каждой привязке таблицы нужен собственный префикс `keybind = ` (голая строка
  `scroll-mode/j=...` отклоняется как неизвестное поле), а `[` надо писать как
  `scroll-mode/[=<action>`: парсер таблицы ищет `/` до первого `=`, поэтому
  `scroll-mode/[/jump_to_prompt:-1` разбирается как таблица `scroll-mode` с
  испорченным ключом `[/jump_to_prompt:-1`.

`jump_to_prompt` требует метки OSC 133 от `shell-integration` (интеграция fish их
ставит).

### Выделение и копирование

* Выделение мышью ведёт себя как в alacritty: `copy-on-select` по умолчанию
  `primary` на Linux, то есть выделение попадает в **PRIMARY**, а не в CLIPBOARD.
  Вставлять его — `shift+insert` (или средняя кнопка мыши); `ctrl+shift+v`
  вставляет CLIPBOARD.
* `ctrl+shift+c` кладёт выделение в CLIPBOARD как `mixed` (plain-текст +
  `text/html`); `ctrl+shift+y` и `scroll-mode/y` намеренно используют `plain` —
  `mixed` построил бы мегабайты HTML для дампа всей истории.
* Выделение остаётся видимым после копирования (`selection-clear-on-copy = false`,
  значение по умолчанию), но сбрасывается, как только вы начинаете печатать
  (`selection-clear-on-typing = true`). Снять вручную: `escape` или один клик.
* **Нет keyboard-action, который начинает выделение диапазона**: `adjust_selection`
  (по умолчанию `shift+arrows`) только двигает уже существующее выделение и без
  него ничего не делает, поэтому `shift+arrows` на чистом экране — no-op.
  Единственное выделение с клавиатуры — `ctrl+shift+a` / `ctrl+shift+y` (всё);
  после этого `shift+arrows` всё ещё может его подправить. Для конкретного
  диапазона используйте copy-mode tmux ниже.
* Цвета выделения прописаны в файлах тем (тёмная `#3c3836`, светлая `#d5c4a1`)
  вместо дефолтной инверсии клетки в ghostty, из-за которой на тёмной теме
  подсветка была такой же яркой, как фон светлой темы. Курсор сохраняет
  дефолтную инверсию, ровно как в alacritty. `verify.sh` сверяет оба значения с
  `[colors.selection]` в темах alacritty.

### Дамп скроллбека

* `ctrl+shift+space`, затем `y` — **весь** скроллбек в буфер. В 1.3.1
  `select_all` берёт историю, а не только видимый экран (замерено: 400 строк
  вывода → 399 переводов строки), хотя reference для этого action говорит «text
  on the screen».
* `ctrl+shift+space`, затем `w` — ghostty пишет скроллбек plain-текстом (длинные
  строки не переносятся) в `/tmp/<random>/history.txt` и копирует **этот путь** в
  буфер; дальше в nvim: `:e ` + `ctrl+shift+v`. У `write_scrollback_file` три
  режима: `copy` (используется здесь), `paste` (впечатывает путь в промпт) и
  `open` — он отдаёт путь в `xdg-open`, см. следующий пункт.
  Комбинация `chain=text:nvim ` + `paste` невозможна: конфиг обрезает
  завершающие пробелы, поэтому `text:nvim ` приходит как `nvim` (проверено через
  `od -c`).
* `ctrl+alt+o` — **весь скроллбек в nvim одной клавишей**:
  `write_scrollback_file:open` → `xdg-open <путь>` → шим `~/.local/bin/xdg-open`
  (`applications/xdg-open`) → `ghostty +new-window -e nvim <путь>`. Открывается
  новое окно того же инстанса ghostty (D-Bus), с той же темой и конфигом, `:q`
  возвращает к терминалу. Шим — единственный способ запустить процесс из
  keybind: в ghostty нет action'а `spawn`/`exec`, а `new_split` принимает только
  направление, `new_window` — ничего, поэтому «сплит с редактором» из keybind
  невозможен (вручную: `w` → `ctrl+shift+o` → `nvim ` + `ctrl+shift+v`).
  Почему шим, а не XDG: `text/plain` в `mimeapps.list` привязан к Helix, и
  менять эту ассоциацию глобально ради дампов не нужно — шим перехватывает
  ровно `$TMPDIR/<22 симв. base64url>/{history,screen,selection}.txt` и
  делегирует всё остальное в `/usr/bin/xdg-open`.
* Только видимый экран: `ctrl+shift+j` (`write_screen_file:paste,plain`),
  `ctrl+alt+shift+j` — открыть его в nvim тем же шимом, `super+ctrl+shift+j` —
  скопировать путь.
* **Внутри полноэкранного TUI (opencode, htop, vim, less) «полного скроллбека»
  не существует**: приложение работает в alternate screen и перерисовывает одну
  сетку, истории там не бывает ни в ghostty, ни в tmux. Для `loc=history`
  ghostty в alt-screen вообще возвращает null — файл не создаётся, `xdg-open` не
  вызывается, `ctrl+alt+o` и `w` молча ничего не делают. Работает только
  `ctrl+alt+shift+j` (видимый экран) и собственные средства приложения:
  `prefix e` в tmux, `/export` (`ctrl+x x`) и `ctrl+z` (`terminal_suspend`) в
  opencode.

### Ghostty + tmux

Зачем сверху tmux: сервер tmux держит собственный скроллбек на панель и переживает
окно терминала (detach/reattach, обрыв SSH). Для терминала важно то, что **tmux
перерисовывает экран**, поэтому вьюпорт ghostty содержит только то, что нарисовал
tmux — скроллбек ghostty внутри tmux почти пуст, и `j`/`k` в `scroll-mode` или
`shift+page_up` прокручивают почти ничего. Внутри tmux:

| цель                          | как                                                       |
|-------------------------------|-----------------------------------------------------------|
| прокрутить панель             | `prefix [` — copy-mode, vi-клавиши (`setw -g mode-keys vi`) |
| поиск по истории панели       | в copy-mode: `/` вниз, `?` вверх, `n` / `N` следующий/предыдущий хит |
| скопировать диапазон          | в copy-mode: `space` начинает, `v` — блочный режим, `y`/`Enter` копируют и выходят |
| скопировать в системный буфер | то же — через `wl-copy`, где он есть, иначе tmux сам шлёт OSC 52 (headless-хост), см. **SSH: terminfo и клипборд** |
| вся история панели в nvim     | `prefix e` (для alt-screen приложений — только видимый экран, см. ниже) |
| новый шелл в том же каталоге  | `prefix v` (рядом), `prefix w` (новое окно)               |

Обратите внимание: `prefix v` привязан к `split-window -h` — вертикальный
разделитель, панели рядом; в стоковом tmux для этого `%` и `"`, и оба здесь
отвязаны. `prefix h` выглядит как горизонтальный аналог, но это **не так**: он
встречается в `.tmux.conf` дважды — сначала `split-window -v`, затем
`select-pane -L`, и побеждает поздняя привязка, поэтому `prefix h` — навигация по
панелям. Для второго сплита используйте `prefix v` ещё раз или добавьте
отдельную клавишу (например `|` и `-`), если нужен горизонтальный сплит.

`prefix e` — аналог ghostty-шного `w`: он запускает `capture-pane -S -20000 -J`
(весь `history-limit`, `-J` склеивает перенесённые строки, чтобы в файле не было
рваных длинных строк), сохраняет в `/tmp/tmux-scroll.txt` и открывает в
`display-popup` 90%×90%, запуская `nvim /tmp/tmux-scroll.txt`. Файл
перезаписывается при каждом использовании, поэтому ничего не накапливается.
Оговорка про alt-screen: для полноэкранного TUI (opencode, htop, vim) панель
хранит только видимую сетку, поэтому «вся история» — это история main screen
плюс текущий экран; проверить: `less README.ru.md` в панели → `prefix e` даёт
~24 строки, а не 600+.

Другие настройки tmux, взаимодействующие с терминалом: `history-limit 20000`
(соответствует перспективе ghostty), `set-clipboard on` (пробрасывает OSC 52 от
приложений), `escape-time 0`, `terminal-overrides alacritty:Tc` для
fallback-терминала (ghostty умеет truecolor без оверрайда). Палитра tmux следует
за темой рабочего стола — см. **Tmux** ниже.

### SSH: terminfo и клипборд

`ssh` всегда передаёт `TERM` клиента (он едет в pty-запросе, а не через
`AcceptEnv`), поэтому сессия, начатая из ghostty, приезжает на сервер как
`TERM=xterm-ghostty`. Если этой записи нет в terminfo удалённого хоста, tmux
вообще не стартует:

```
$ tmux new -s work
missing or unsuitable terminal: xterm-ghostty
```

Эта же запись решает, будет ли работать клипборд: tmux нужна возможность `Ms`,
чтобы выставить терминальный клипборд последовательностью OSC 52. Обе проблемы
закрывает одна строка в `ghostty/config.ghostty`, и на серверах руками ничего
ставить не нужно:

```
shell-integration-features = ssh-terminfo
```

Обёртка `ssh` из shell-integration (`ghostty +ssh`) при первом подключении
пайпит встроенную в ghostty запись в `tic -x -` на удалённом хосте:
`~/.terminfo/x/xterm-ghostty`, под твоим пользователем, без root. Успех
кэшируется в `~/.cache/ghostty` (сброс — `ghostty +ssh-cache`), поэтому новый
сервер лечится сам. Если поставить не удалось (нет `tic`, read-only home),
ghostty откатывается на `TERM=xterm-256color` и сессия остаётся рабочей.
Неперечисленные фичи сохраняют дефолты структуры (`cursor`, `title`, `path`
включены; `ssh-env`, `sudo` выключены), поэтому одна названная фича не
отключает остальные.

Не подменяйте эту запись `ghostty` из ncurses 6.6: в ней нет `Tc`, и tmux
показывает `#{client_termfeatures}` без `RGB`, то есть без truecolor внутри
tmux. В собственной записи ghostty есть и `Tc`, и `Ms`.

Клипборд через SSH:

| направление | путь |
|-------------|------|
| копирование внутри tmux (copy-mode, `y`) | буфер tmux → OSC 52 → ghostty кладёт в локальный клипборд |
| копирование из приложения в панели (nvim `clipboard=osc52`) | `set-clipboard on` принимает последовательность и пробрасывает её клиенту |
| вставка в удалённый шелл | локальный `ctrl+shift+v`, bracketed paste по сети — OSC 52 не нужен |
| чтение локального клипборда на сервере (nvim `"+p`) | OSC 52 read, регулируется `clipboard-read` |

`clipboard-write` по умолчанию `allow`, поэтому запись идёт без подтверждения;
`clipboard-read` по умолчанию `ask`, и в конфиге стоит `allow`, чтобы не
подтверждать каждый `"+p`. Это осознанный компромисс: при `allow` любой процесс
на сервере сможет прочитать локальный клипборд.

Headless-хостам для этого `wl-copy` не нужен: привязка `y` пайпит через
`wl-copy`, если он есть, а если нет — пайп молча падает, но tmux всё равно
заполняет буфер и шлёт OSC 52. Копирование из copy-mode продолжает работать —
проверено на `awdesk` (headless, без Wayland) с `tmux 3.8`.

### CLI

Полезная диагностика:

```sh
ghostty +validate-config          # должен быть *глобальным* флагом: сначала --config-file=...
ghostty +show-config --docs       # текущие значения с встроенным мануалом
ghostty +list-actions             # все action с синтаксисом аргументов
ghostty +list-keybinds --default --docs
ghostty +list-themes              # имена встроенных тем
ghostty +list-fonts
ghostty +ssh-cache                # забыть, на какие хосты terminfo уже залит
```

`+validate-config` молча возвращает 1, если файл передан после action
(`ghostty +validate-config --config-file=…` даёт 1 без диагностики), поэтому
всегда пишите `ghostty --config-file=… +validate-config`. Это ловит опечатки и
неверные типы значений (`…/b.conf:1:totally-bogus-option: unknown field`,
exit 1), так что запускайте после каждой правки конфига — та же проверка есть в
`install/verify.sh`.

## Runtime state и переключение темы

Репозиторий — **источник конфигурации только для чтения**: ни одно приложение в
него не пишет. Merge-каталоги (`fish`, `helix`, `opencode`) дают приложениям
настоящий каталог для записи рядом с отслеживаемыми файлами, поэтому runtime state
остаётся вне дерева. Всё, что меняется в рантайме, живёт в одном фиксированном
каталоге:

```
~/.local/state/dotfiles/
  background-mode                      # "dark" или "light"
  alacritty.toml                       # [general] import палитры
  rofi.rasi                            # @theme для rofi
  helix/runtime/themes/dotfiles.toml   # тема "dotfiles" (наследует gruvbox_*)
  ironbar/colors.css                   # палитра @define-color
  ironbar/style.css                    # обёртка: colors.css + style.css из репо
  mattermost.log                       # лог wayland/mattermost-theme (если есть)
  theme-hooks.log                      # вывод хуков + коды возврата
```

Путь захардкожен (не `$XDG_STATE_HOME`): alacritty и rofi не раскрывают
переменные окружения в путях `import`/`?import`.

**Переключение.** darkman вызывает `~/.local/share/darkman/theme` с `dark|light`;
хук показывает уведомление и запускает `wayland/theme-sync <mode>`. `theme-sync`
только пишет state-файлы выше и рассылает хуки — про отдельные приложения он
ничего не знает. Каждый хук в `wayland/theme-hooks.d/` вызывается как

```
<NN>-<app>.sh <dark|light>
```

с `THEME_STATE`, `THEME_HOOK_LOG`, `THEME_PREV_MODE` и `THEME_GUI` в окружении,
под `timeout 15`. Хук сам решает, применим ли он (приложение не установлено или
не запущено → `exit 0`, что не считается ошибкой), никогда не пишет в репозиторий,
а его падение только логируется в `~/.local/state/dotfiles/theme-hooks.log` — оно
не может сломать переключение. Добавить приложение — значит положить новый файл в
этот каталог; `theme-sync` остаётся нетронутым.

| хук                | что делает                                                          |
|--------------------|---------------------------------------------------------------------|
| `10-gtk.sh`        | `gsettings`: `adw-gtk3(-dark)` + `color-scheme` (сигнал, за которым следует каждое libadwaita-приложение) |
| `20-ghostty.sh`    | `SIGUSR2` запущенному ghostty (перечитывание конфига; цвета применяются на лету) |
| `25-alacritty.sh`  | `alacritty msg config` для палитры + прозрачности (fallback-терминал) |
| `30-helix.sh`      | `SIGUSR1` (helix перезагружает конфиг и тему)                       |
| `40-tmux.sh`       | `tmux set -s theme` для запущенного сервера + обновление статус-строки |
| `50-fish.sh`       | `SIGWINCH` для fish, чтобы нарисованный промпт перерисовался сразу  |
| `60-redraw.sh`     | `SIGWINCH` для TUI с ANSI-цветами (`htop`, `less`, `ncdu`; расширяется через `DOTFILES_THEME_REDRAW`) |
| `90-mattermost.sh` | перезапуск Mattermost, только если `THEME_PREV_MODE` действительно отличается |

Общие хелперы лежат в `wayland/theme-hook-lib.sh` (`theme_have`, `theme_running`,
`theme_gui`, `theme_log`, `theme_state_dir`). У Neovim хука нет намеренно: он сам
следит за state-файлом (см. **Neovim** ниже).

После хуков `theme-sync` в фоне перезапускает `wayland/wallpapers.sh`, поэтому
обои переключаются на картинку соответствующего режима
(`THEME_SYNC_NO_WALLPAPER=1` отключает).

**Mattermost.** `wayland/theme-hooks.d/90-mattermost.sh` вызывает
`wayland/mattermost-theme <mode>`, когда существует
`~/.config/Mattermost/config.json` и есть живая графическая сессия (wayland- или
X11-сокет — IPC композитора не нужен, так как приложение лишь перезапускается в
эту сессию). Хук — no-op, если `THEME_PREV_MODE` не отличается от нового режима,
поэтому `verify.sh` и повторный `theme-sync` с текущим режимом никогда не
перезапускают приложение:

- тема чата **не** хранится локально: это серверная пользовательская настройка
  (категория `theme`, значение — весь JSON пресета, а не его имя), поэтому скрипт
  пишет `theme/{dark,light}/mattermost.json` — Onyx и Quartz из Mattermost
  v10.10.1 — через `PUT /api/v4/users/<id>/preferences` для каждого сервера из
  `config.json`. Токен сессии и user id читаются только для чтения из
  `~/.config/Mattermost/Cookies` и никуда не копируются;
- оформление окна следует `darkMode` в `config.json` (Electron-таббар, иконка в
  трее, overlay заголовка), а `themeSyncing` не трогается: при значении по
  умолчанию `false` десктопное приложение сохраняет
  `nativeTheme.themeSource = "system"`, то есть следует GTK-схеме, которую
  `theme-sync` уже выставил выше. Включение `themeSyncing` заставит окно взять
  серверную тему чата, что тоже работает — скрипт не перезаписывает этот выбор;
- `config.json` читается только при старте, а Electron перезаписывает его при
  выходе, поэтому порядок такой: `kill → API + config.json → start`. Приложение
  перезапускается (`SIGTERM`, затем `SIGKILL` через 5 с) только если оно было
  запущено;
- сетевые ошибки и ошибки сессии логируются в
  `~/.local/state/dotfiles/mattermost.log` и никогда не ломают переключение.
  `MATTERMOST_THEME_NO_RESTART=1` пишет настройку и конфиг, не трогая процессы,
  `THEME_SYNC_NO_MATTERMOST=1` пропускает хук, а `THEME_SYNC_NO_RELOAD=1`
  пропускает перезагрузку состояния и все хуки (поэтому `verify.sh` остаётся без
  побочных эффектов).

**Ручное переключение.** `theme-switch [dark|light]` (`applications/theme-switch`,
симлинк в `~/.local/bin`) — тонкая обёртка над `theme-sync`; без аргумента она
инвертирует режим, записанный в `background-mode`. Работает и на профиле
`headless`: `theme-sync` сам пишет state-файлы и пропускает GUI-перезагрузки. Она
**не** перекрашивает эмулятор терминала на стороне SSH-клиента — палитра
foreground/background клиента вне контроля сервера; за темой следуют только цвета
текста, которые выводят приложения (синтаксис fish, helix, tmux).

rofi подхватывает тему при следующем запуске, fish применяет её на следующем
промпте, а ironbar перезагружается сам, потому что изменилась сгенерированная
обёртка. Ни одно приложение не нужно перезапускать.

**Merge-каталоги.** `~/.config/fish` и `~/.config/helix` — настоящие каталоги,
файлы которых являются симлинками в репозиторий (тег `merge` в `symlinks.conf`).
Файлы из `install/volatile.conf` (`fish_variables`, `fish_frozen_*.fish` от fish,
файлы, управляемые fisher) вместо этого копируются: локальная копия никогда не
перезаписывается, а старый симлинк в репозиторий заменяется копией при первой
установке. Добавьте туда новый runtime-файл, если приложению нужно писать рядом с
отслеживаемым; поддерживаются глобы `*`.

**Helix.** `~/.config/helix/runtime` — симлинк на state-каталог, а
`helix/config.toml` задаёт `theme = "dotfiles"`. Helix ищет темы в
`$XDG_CONFIG_HOME/helix/runtime/themes` без необходимости `HELIX_RUNTIME`, поэтому
тема работает независимо от способа запуска helix (desktop entry, терминал, другой
WM).

**Ironbar.** Он всегда запускается с `-t <state>/ironbar/style.css`; палитра в
`colors.css`, а в репозитории в `ironbar/style.css` остаётся только раскладка без
единого `@define-color`. Watcher следит за обёрткой, поэтому после правки
стилей в репозитории перезапустите `theme-sync` (или коснитесь обёртки), чтобы
перезагрузить.

**Ghostty.** Здесь описана только тема — шрифты, привязки клавиш, скроллбек,
выделение и работа с tmux в разделе **Ghostty** выше. `~/.config/ghostty` —
симлинк на `ghostty/`, конфиг — `config.ghostty` (легаси-файл `config` не должен
существовать: ghostty загрузил бы оба и выдал предупреждение), палитры —
`ghostty/themes/gruvbox-{dark,light}`, обычные конфиг-сниппеты с теми же
gruvbox-hex, что и в `alacritty/themes/themes/` (проверяется `verify.sh`).

Имена тем — это имена файлов **без** расширения: ghostty ищет ровно
`$XDG_CONFIG_HOME/ghostty/themes/<name>`, поэтому файлы называются
`ghostty/themes/gruvbox-dark` и `gruvbox-light` (суффикс `.conf` молча не
находится).

Конфиг использует `theme = light:gruvbox-light,dark:gruvbox-dark`: ghostty сам
выбирает файл и следует за `gsettings ... color-scheme` через libadwaita,
перезагружаясь при смене схемы — проверено на 1.3.1, фон меняется без всякого
хука. `20-ghostty.sh` (`SIGUSR2`) нужен для правленых файлов палитр и как
страховка, если libadwaita не увидел схему.

Шрифт, padding и прозрачность подогнаны под alacritty намеренно, чтобы терминалы
выглядели одинаково: alacritty не задаёт семейство шрифта, поэтому получает
`monospace` из fontconfig (на этой машине `Noto Sans Mono`, размер 11.25 по
умолчанию) — `font-family = Noto Sans Mono` с `JetBrains Mono` как fallback и
`font-size = 11.25`; `window-padding-x/y = 0`, потому что у alacritty
`window.padding` по умолчанию `{0,0}`, а у ghostty — 2;
`background-opacity-cells = true`, потому что alacritty делает прозрачным всё
окно через композитор, тогда как ghostty по умолчанию делает прозрачными только
клетки без явного фона.

Цвета выделения прописаны в файлах тем вместо того, чтобы полагаться на
дефолтную инверсию клетки ghostty (тёмная `bg1` `#3c3836`, светлая `bg2`
`#d5c4a1`; обоснование — в **Ghostty → Выделение и копирование**), а `cursor-*`
остаётся незаданным, чтобы курсор сохранял дефолтную инверсию, ровно как в
alacritty. `verify.sh` сверяет оба hex-значения выделения с `[colors.selection]`
в темах alacritty, чтобы fallback-терминал совпадал.

**Neovim.** `nvim/lua/theme.lua` следит за `~/.local/state/dotfiles` через
`vim.uv.new_fs_event` (debounce 80 мс, fallback `new_fs_poll`), поэтому уже
запущенные редакторы переключаются без внешнего бинарника и RPC-сокета — старая
ветка `nvim-ctrl` в `theme-sync` никогда не работала, бинарник нигде не был
установлен. При изменении он выставляет `vim.o.background` и заново запускает
`:colorscheme`: gruvbox.nvim читает `background` только в `load()` и не слушает
`OptionSet`.

**Fish.** `fish_variables` и плагины fisher локальны для `~/.config/fish` и не в
git; декларативный список плагинов остаётся в `fish/fish_plugins`.
`fish/conf.d/theme.fish` применяет тему из `background-mode` на промпте
(`fish/themes/dark.theme` / `light.theme`, gruvbox-палитры с явными hex-цветами),
поэтому старая универсальная переменная `background_mode` удалена, а цвета промпта
меняются, не полагаясь на ANSI-палитру терминала. `wm` пишет
`~/.local/state/dotfiles/compositor` — тот же файл, который засевает установщик —
и больше не трогает универсальные переменные. `theme.fish` также включает
`fish_handle_reflow 1`: без этого fish 4.x игнорирует `SIGWINCH` в терминалах,
которые переливают текст, и уже нарисованный промпт сохранял бы старую тему до
следующего `Enter`. Плата — перерисовка промпта при каждом изменении размера окна.

**Tmux.** `.tmux.conf` держит обе палитры инлайн как `dark-theme-*` /
`light-theme-*` (значения взяты из gruvbox-тем alacritty), а стили используют
имена `theme*`, поэтому tmux перекрашивается сам, когда меняется тема клиента. Это
требует tmux >= 3.8 (`theme`, `theme*` и хуки `client-light-theme` /
`client-dark-theme`); более старые версии через `%if` падают на прежнюю статичную
палитру Solarized. Ни state-файла, ни `source-file` нет: `theme` — серверная
опция, и `40-tmux.sh` запускает `tmux set -s theme <mode>` только если сервер уже
работает. tmux не замечает изменение сам — alacritty отвечает на `OSC 11`, но не
реализует `DECSET 2031`, поэтому серверу нужно сказать явно (ghostty реализует
2031, но хуку это не мешает). Учтите, что `theme` действует на весь сервер,
поэтому все клиенты одного сервера делят один режим.

**Waybar.** Он не участвует в переключении и остаётся в rollback-режиме со своей
статичной палитрой. Чтобы вернуть его, сделайте то же самое: сгенерируйте обёртку
в state-каталоге, запускайте `waybar -s <state>/waybar/style.css` и `@import`
палитру.

**Проверки.** `./install/verify.sh` проверяет, что state-файлы соответствуют
текущему режиму, что merge-каталоги и симлинки разложены правильно, что нет
висячих ссылок и легаси-хуков, и что переключение темы оставляет `git status`
неизменным (он только читает и восстанавливает текущий режим). Ещё он проверяет,
что `~/.local/bin/theme-switch` указывает в репозиторий, что легаси-переменная
`background_mode` не выставлена, что каждый файл в `wayland/theme-hooks.d/`
исполняемый и синтаксически корректен, что файлы тем ghostty существуют и их
палитры всё ещё совпадают с alacritty, и что хуки последнего переключения все
завершились с кодом 0.

**Ограничения.** `XDG_STATE_HOME` должен оставаться по умолчанию. fish
перерисовывается через `SIGWINCH`, helix перезагружается по `SIGUSR1` (новые окна
helix подхватывают сразу), neovim — своим watcher'ом, ghostty — по `SIGUSR2`
(уже открытые окна перерисовываются), rofi — при следующем запуске, tmux — при
`theme-sync` (запущенный сервер обновляется на месте, сервер, запущенный позже,
подхватывает режим при подключении).

## OpenCode / MCP

`opencode/` — merge-каталог (как `fish/` и `helix/`): `opencode.jsonc`, `cli.json`,
`AGENTS.md`, `plugins/` и `sync-models.sh` — симлинки в репозиторий, а то, что
OpenCode пишет рядом со своим конфигом — `package.json`, `bun.lock`,
`node_modules/`, `service.json` — остаётся настоящим локальным файлом и никогда не
попадает в рабочее дерево. MCP-серверы объявлены в `mcp.servers` в
`opencode/opencode.jsonc`:

| сервер     | транспорт | назначение                                                                |
|------------|-----------|---------------------------------------------------------------------------|
| `vision`   | local     | `analyze_image` через любую мультимодальную модель (`mcp-vision-bridge`)  |
| `web-docs` | local     | документация по API/библиотекам: `lib_docs`, `search_docs`, `fetch_url`, `web_search`, `list_docs` |
| `deepwiki` | remote    | `read_wiki_structure`, `read_wiki_contents`, `ask_wiki_question` для публичных GitHub-репозиториев |
| `docs`     | remote    | внутренний documentation MCP                                              |

`web-docs` не опубликован на npm, поэтому установщик клонирует
[web-docs-mcp](https://github.com/Aleksandrr/web-docs-mcp) в
`~/.local/share/web-docs-mcp` (переопределяется через `WEB_DOCS_MCP_DIR` или
`LOCAL_PREFIX`), ставит его runtime-зависимости и патчит один апстрим-баг: его
конвертер схем эпохи zod v3 оставляет каждый `enum` пустым под zod v4, из-за чего
`ecosystem`, `target` и `subdir` были непригодны (патч трогает только эти два
файла и восстанавливается перед `git pull`, затем применяется снова).
Скачанный markdown идёт в `~/.local/share/web-docs-mcp/docs`, TTL-кэш — в
`~/.cache/web-docs-mcp`, вне и клона, и репозитория dotfiles, поэтому обновления
никогда не трогают сохранённые доки, а конфиги остаются только для чтения.

`deepwiki` — официальный бесплатный удалённый сервер
(`https://mcp.deepwiki.com/mcp`, без аутентификации, `oauth: false`). Он принимает
только `owner/repo`; сопоставление имени пакета с репозиторием даёт `web-docs`
(`lib_docs` возвращает поле `repository`).

Разделение зафиксировано в `opencode/AGENTS.md`: `web-docs` — для фактов по API,
`deepwiki` — для архитектуры и более глубокого анализа, и только затем исходники.

### Модели по агентам

`default_agent` — `plan`, корневая `model` —
`routerai/~deepseek/deepseek-v4-pro-latest`, поэтому новая сессия начинается на
plan-модели. `agents.plan` повторяет эту модель, `agents.build` ставит
`routerai/~deepseek/deepseek-v4-flash-latest#low`, а `agents.compaction` держит
дешёвую flash-модель.

V2 резолвит модель сессии один раз (сохранённая модель сессии, иначе дефолт
каталога) и не перечитывает `agents.<id>.model` при смене агента, поэтому переход
plan → build сам по себе оставляет старую модель. `opencode/plugins/agent-model-sync.ts`
закрывает этот пробел: при приёме промпта, то есть до резолва модели, он
переключает сессию на модель активного агента, если агент сменился или у сессии
ещё нет модели. Модель, выбранная вручную для сессии, выживает до следующей смены
агента. Исходники плагинов кэшируются по пути, поэтому после правки файла
запустите `opencode service restart` (простой `opencode reload` может продолжать
отдавать старую сборку; переименование файла всегда заставляет взять свежую).

## Установка

```sh
./install/install.sh                 # автоопределение хоста
./install/install.sh --host desktop  # явный хост
./install/install.sh --dry-run       # только показать действия
./install/install.sh --no-packages   # только (пере)линковать конфиги
./install/install.sh --no-links      # только установить пакеты
./install/install.sh --no-shell      # оставить текущую login-оболочку
./install/install.sh --no-nvim       # пропустить подготовку плагинов/парсеров
```

Установщик:
1. ставит `yay`, если его нет,
2. `yay -S --needed` из `packages/base.txt` (+ `packages/dev.txt`, если профиль
   не `headless`, + `packages/gui.txt` для GUI, + `hosts/<host>/packages.txt`),
3. `npm install -g --prefix ~/.local` из `npm.txt` (дефолтный префикс npm —
   принадлежащий root `/usr`), `uv tool install` из `uv-tools.txt` и клонирует
   `web-docs-mcp` в `~/.local/share/web-docs-mcp` с его runtime-зависимостями и
   патчем enum для zod-4 (это MCP-сервер `web-docs`; npm-пакета не существует),
4. раскладывает симлинки по `symlinks.conf` — merge-каталоги разворачиваются в
   настоящие каталоги с пофайловыми ссылками, volatile-файлы копируются — сохраняя
   всё заменяемое в `~/.dotfiles-backup-<timestamp>/`,
5. создаёт `~/.local/state/dotfiles/`, линкует `~/.config/helix/runtime` на него и
   пишет `compositor` (см. [Композиторы](#композиторы-sway--niri)) — один раз
   засевается из существующей `WAYLAND_COMPOSITOR`, дальше владеет `wm`,
6. делает fish login-оболочкой (`sudo chsh`; пропустить через `--no-shell`) — весь
   GUI-путь начинается с `fish/config.fish`, так что bash-логин оставляет чёрный
   TTY,
7. ставит fisher + плагины из `fish/fish_plugins` в `~/.config/fish` (после
   линковки; пропускается для `headless` и через `--no-fisher`),
8. применяет текущий режим darkman через `wayland/theme-sync`
   (`--no-packages` всё равно выполняет шаги 4–8),
9. подготавливает плагины Neovim и парсеры treesitter, один раз запуская
   `nvim --headless` (`NVIM_TS_INSTALL_SYNC=1`, чтобы парсеры собирались во время
   установки, а не при первом интерактивном старте; пропустить через `--no-nvim`).
   Плагины не являются pacman-пакетами: ими управляет `vim.pack.add()` в
   `nvim/lua/plugins.lua`, версии закреплены в `nvim/nvim-pack-lock.json`.
   Git-ревью (хуки, stage, diff перед коммитом) — см. `nvim/README.md`.

Профиль `headless` ставит только базовый набор плюс fish/opencode/редакторы и их
зависимости — без GUI, без Sway. Dev/DevOps-инструменты можно подключить на
конкретном хосте через `hosts/<host>/packages.txt`.

Установка пакета не запускает его: после чистой установки включите Docker-демон и
добавьте себя в его группу (нужен релогин):

```sh
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

## Cleanup (пакеты не из манифестов)

`install/cleanup.sh` — аналог установщика с обратным знаком: он удаляет пакеты,
которые явно установлены, но отсутствуют в манифестах, и опционально чистит то,
что они оставляют (конфиги, state, кэши, сервисы). Он использует тот же
`install/lib.sh` и то же определение хоста/профиля, поэтому наборы «ставить» и
«оставлять» не могут разъехаться.

```sh
./install/cleanup.sh                     # dry-run: таблица кандидатов
./install/cleanup.sh --check             # exit 0 — дрейфа нет, 2 — есть
./install/cleanup.sh --apply             # спросить один раз, затем удалить
./install/cleanup.sh --apply --purge-configs --purge-caches
./install/cleanup.sh --apply --interactive   # спрашивать по каждому пакету
./install/cleanup.sh --init-keep         # черновик hosts/<host>/keep.txt
```

Набор кандидатов — это `pacman -Qqe` минус:

1. **desired** — манифесты для текущего хоста/профиля (base, +dev если не
   `headless`, +gui, +дополнения хоста);
2. **protected** — `install/protected.txt`: ядро, загрузчик, прошивки, init, auth,
   сетевой стек, `yay`. Отсюда не удаляется ничего и никогда;
3. **keep** — `hosts/<host>/keep.txt` (личные приложения) плюс `--keep <pkg>`.
   Формат — одно имя в строке; всё после `#` игнорируется, поэтому черновик из
   `--init-keep` (`# pkg  # 12.8 MiB`) можно раскомментировать как есть;
4. пакеты, от которых зависит что-то остающееся. Это вычисляется до неподвижной
   точки по `pacman -Qi → Required By` (что включает зависимости через provides,
   например `fuse2 ← ntfs-3g`), затем проверяется самим pacman через
   `pacman -Rs --print`; всё, что он откажется удалять, попадает в отчёт
   «остаются в системе» с причиной.

`--apply` сначала отключает systemd-юниты удаляемых пакетов (их unit-файлы исчезнут
вместе с пакетом), затем запускает одну транзакцию `pacman -Rns` (с откатом на
поштучное удаление), удаляет зависимости, ставшие сиротами (`pacman -Qtdq`,
отключается `--no-orphans`), и сносит висячие симлинки `*.wants`.

Ничего не удаляется безвозвратно. `--purge-configs` и `--purge-system`
**перемещают** оставшиеся пути в карантинный каталог и никогда не трогают то, чем
управляет репозиторий dotfiles (симлинки в репозиторий, цели из `symlinks.conf`,
state-каталог) или что поставляет всё ещё установленный пакет (`pacman -Qo`). Пути
берутся из `install/cleanup-paths.conf` плюс эвристика, сопоставляющая записи
верхнего уровня `~/.config`, `~/.local/share`, `~/.local/state`, `~/.cache` с
именем пакета без учёта регистра и разделителей (`Code` ~ `code`). Эвристика
отступает, если каталог может принадлежать остающемуся пакету
(`~/.config/Mattermost` остаётся, пока удаляется только сервер `mattermost`, а
`mattermost-desktop` остаётся).

Флаги `--purge-*` действуют только вместе с `--apply`; в dry-run они печатают,
что было бы перемещено и какого размера. Они работают по объединению текущего
набора кандидатов и `removed.txt` **всех** предыдущих прогонов, поэтому остатки
можно почистить после того, как пакеты уже удалены —
`cleanup.sh --apply --purge-configs` валиден, даже когда он сообщает «удалять
нечего».

`--purge-caches` чистит кэши пакетов и пересобираемые данные (`paccache -r -k3`,
`yay -Sc`, journal → 500 МиБ, кэши npm/uv/pip, миниатюры, fontconfig, кэш
`web-docs-mcp`); `--purge-modcache` дополнительно сносит кэш Go-модулей и реестр
Cargo (оба перекачиваются при следующей сборке); `--purge-tools` удаляет
глобальные npm-пакеты, `uv tool`-и и плагины fisher, которых нет в `npm.txt`,
`uv-tools.txt` и `fish/fish_plugins`.

Каждый применённый прогон оставляет
`~/.local/state/dotfiles/cleanup/<timestamp>/` с `removed.txt`, `orphans.txt`,
`log.txt`, `report.md`, исполняемым `restore.sh` (`yay -S --needed …`) и самим
карантином:

```sh
~/.local/state/dotfiles/cleanup/20261017-180000/
  removed.txt  orphans.txt  log.txt  report.md  restore.sh
  quarantine/home/.config/Code/...      # перемещено, не удалено
  quarantine/root/var/lib/...           # только с --purge-system
```

`restore.sh` создаётся только если прогон действительно что-то удалил;
прогон только с purge оставляет пустой `removed.txt` и сообщает, что удаления в
этом прогоне не было.

`CLEANUP_CHECK=1 ./install/verify.sh` дополнительно сообщает о дрейфе пакетов как
о предупреждении (это не фатально: на личной машине ожидаемо есть лишние
приложения).

## VPN

Профиль `ntech` OpenVPN/NetworkManager лежит в репозитории как **скелет без
секретов** (`vpn/ntech.nmconnection.in`). Сертификаты/ключи остаются в `~/vpn`,
пароль — в кейринге, а локальный логин/эндпоинты — в игнорируемом git
`vpn/local.env`. Подробности в `vpn/README.md`.

```sh
cp vpn/local.env.example vpn/local.env   # затем отредактировать
./install/install_vpn.sh --check
./install/install_vpn.sh
```
